# Topic 09.04 — ORM and Database Migrations

## Learning goal

Understand how an application maps Python objects to relational database tables, how an ORM executes database work, and why production schema changes require migrations.

This topic builds on:

- database tables and constraints;
- SQL queries;
- repositories;
- database connections, sessions, and pools.

---

## 1. Why do ORMs exist?

An application is usually written using objects and functions:

~~~python
product = Product(name="Keyboard", price=2500)
~~~

A relational database stores rows and columns:

~~~text
products
--------------------------------
id | name     | price
101| Keyboard | 2500
~~~

The application and database use different representations.

An Object-Relational Mapper, or ORM, is a library that helps translate between them:

~~~text
Python objects
      ↓
ORM
      ↓
SQL statements
      ↓
Relational database
~~~

The ORM does not remove the database. It generates database operations on behalf of the application.

---

## 2. A simple model-to-table mapping

A Python ORM model may represent a database table:

~~~python
class Product:
    id: int
    name: str
    sku: str
    price: float
~~~

The corresponding table may look like:

~~~sql
CREATE TABLE products (
    id INTEGER PRIMARY KEY,
    name TEXT NOT NULL,
    sku TEXT NOT NULL UNIQUE,
    price NUMERIC NOT NULL CHECK (price > 0)
);
~~~

Typical mappings include:

| Application concept | Database concept |
|---|---|
| Class | Table |
| Object instance | Row |
| Attribute | Column |
| Object identifier | Primary key |
| Object relationship | Foreign key |
| ORM query | SQL statement |
| ORM session | Unit of database work |

The exact syntax differs between SQLAlchemy, Django ORM, and other libraries, but the underlying idea is similar.

---

## 3. What happens when an ORM query runs?

Consider an ORM query that means:

~~~python
product = session.get(Product, 101)
~~~

Conceptually, the ORM may generate SQL similar to:

~~~sql
SELECT id, name, sku, price
FROM products
WHERE id = 101;
~~~

The actual flow is:

1. Application calls an ORM method.
2. ORM builds a query expression.
3. ORM generates SQL and query parameters.
4. Driver sends the SQL through a database connection.
5. Database executes the SQL.
6. Driver returns database rows.
7. ORM converts rows into Python objects.
8. Application receives the result.

The ORM hides repetitive SQL construction, but the database still executes SQL.

---

## 4. ORM does not mean “no SQL knowledge required”

An ORM can make common operations easier, but developers still need to understand:

- tables and relationships;
- joins;
- indexes;
- constraints;
- transactions;
- query plans;
- isolation and locking;
- generated SQL;
- data volume and query performance.

A short ORM expression may produce an expensive SQL query.

Technical leads should be able to inspect the SQL generated by the ORM when diagnosing:

- slow endpoints;
- unexpected joins;
- too many queries;
- missing filters;
- N+1 query problems.

---

## 5. Creating, reading, updating, and deleting

Conceptually, an ORM supports CRUD operations:

~~~python
# Create
product = Product(name="Keyboard", sku="KEY-101", price=2500)
session.add(product)

# Read
product = session.get(Product, 101)

# Update
product.price = 2400

# Delete
session.delete(product)

# Persist the unit of work
session.commit()
~~~

The exact behavior depends on the ORM. In many ORMs:

- adding an object places it in a pending state;
- flushing sends SQL to the database;
- committing makes the transaction durable;
- rollback removes uncommitted changes from the transaction.

Calling add does not necessarily mean the row is already permanently stored.

---

## 6. ORM session versus database connection

These terms must not be confused.

### Database connection

A physical communication channel to the database, usually backed by a network socket.

### Database session

The database server's context associated with an authenticated connection.

### ORM session

A library-level unit-of-work object that tracks application objects and coordinates database operations.

An ORM session may borrow a physical database connection only when it needs to communicate with the database. The exact relationship depends on the ORM and configuration.

~~~text
ORM Session
    ↓ borrows
Database connection
    ↓ carries protocol messages
Database session
    ↓ operates on
Database
~~~

An ORM session is not automatically the same thing as a physical database connection.

---

## 7. Unit of work

An ORM session often acts as a unit of work.

A unit of work groups related changes so they can succeed or fail together:

~~~text
Load customer
      ↓
Create order
      ↓
Update inventory
      ↓
Commit all changes
~~~

If an operation fails:

~~~text
Error
  ↓
Rollback the transaction
  ↓
No partial changes remain
~~~

The application must define the transaction boundary carefully. A request should not leave an ORM session or database transaction open after the request completes.

---

## 8. Flush, commit, and rollback

These operations have different meanings.

### Flush

Flush sends pending ORM changes to the database within the current transaction.

The changes may still be uncommitted.

### Commit

Commit finalizes the transaction and makes successful changes durable and visible according to the database's transaction rules.

### Rollback

Rollback discards uncommitted changes in the current transaction.

A simplified lifecycle is:

~~~text
session.add(object)
      ↓
flush → SQL is sent
      ↓
commit → transaction is finalized
      ↓
close/reset → session is no longer used
~~~

If an error happens before commit:

~~~text
rollback → pending transaction changes are discarded
~~~

A successful flush does not guarantee a successful commit. Constraints, conflicts, or connection failures may still cause commit to fail.

---

## 9. Identity map and object state

Many ORMs keep an identity map inside the ORM session.

This means that within one ORM session, the same database row may be represented by one tracked Python object.

An object may move through states such as:

- transient: created in Python but not tracked;
- pending: added to the session but not flushed;
- persistent: associated with a database identity;
- detached: no longer associated with the session;
- deleted: marked for deletion.

The exact state names vary by ORM, but the important idea is:

> An ORM session tracks object state and decides which SQL operations are needed.

This convenience can also surprise developers if a stale object is reused or if changes are flushed implicitly.

## 10. Relationships and foreign keys

Suppose an order belongs to a customer.

The database may represent this as:

~~~sql
CREATE TABLE orders (
    id INTEGER PRIMARY KEY,
    customer_id INTEGER NOT NULL,
    FOREIGN KEY (customer_id) REFERENCES customers(id)
);
~~~

The ORM may expose a relationship:

~~~python
order.customer
~~~

The relationship is not magic. The ORM must execute SQL to load the related customer, usually through a join or a separate query.

Relationships should be designed with:

- correct foreign keys;
- clear ownership;
- appropriate delete behavior;
- explicit loading strategy;
- indexes on foreign-key columns where appropriate.

---

## 11. Lazy loading and eager loading

### Lazy loading

A related object is fetched only when the application accesses it.

Example:

~~~python
orders = session.query(Order).all()

for order in orders:
    print(order.customer.name)
~~~

The first query loads orders. Accessing order.customer may trigger another query for each order.

### Eager loading

The ORM loads related data up front, often with a join or a small number of additional queries.

Eager loading can reduce repeated database calls, but it may fetch more data than needed.

The correct strategy depends on:

- expected result size;
- relationship cardinality;
- fields required by the endpoint;
- query plan;
- memory usage.

---

## 12. The N+1 query problem

Suppose an endpoint loads one hundred orders and then accesses each order's customer.

The application may execute:

~~~text
1 query to load orders
+ 100 queries to load customers
= 101 queries
~~~

This is the N+1 query problem.

It can cause:

- high database load;
- increased response latency;
- pool exhaustion;
- poor performance that is hidden behind simple-looking ORM code.

Possible solutions include:

- eager loading;
- explicit joins;
- batching;
- selecting only required columns;
- changing the response shape;
- using a data-loader pattern.

Always inspect generated SQL and query counts instead of assuming the ORM is efficient.

---

## 13. ORM versus raw SQL

ORM advantages:

- less repetitive CRUD code;
- model and relationship abstractions;
- parameter binding;
- object tracking;
- portability across supported databases;
- integration with application code.

Raw SQL advantages:

- precise control over the query;
- easy use of database-specific features;
- clearer behavior for complex reporting queries;
- sometimes better performance or easier optimization.

ORM risks:

- hidden queries;
- accidental lazy loading;
- inefficient generated SQL;
- confusion around flush and commit;
- abstraction that hides important database behavior.

A mature application may use both. Use the ORM for common application operations and raw SQL where explicit control or database-specific behavior is valuable.

---

## 14. Repository boundary with an ORM

A repository can hide ORM details from the service layer:

~~~text
Router
  ↓
Service
  ↓
Repository
  ↓
ORM session
  ↓
Database
~~~

The service expresses application intent:

~~~python
order_service.create_order(command)
~~~

The repository handles persistence details:

~~~python
order_repository.save(order)
order_repository.find_by_id(order_id)
~~~

This separation helps the service avoid depending on SQL or ORM-specific APIs. However, it should not become an excuse to hide performance problems. The team still needs visibility into generated SQL and transaction behavior.

---

## 15. What are database migrations?

A migration is a versioned, repeatable change to the database schema.

Examples:

- create a new table;
- add a column;
- add an index;
- add a foreign key;
- rename or remove a column;
- change a constraint.

The application model describes what the code expects. A migration changes the database so that the database schema can evolve in a controlled way.

~~~text
Migration 001 → create products table
Migration 002 → add category column
Migration 003 → add index on category
~~~

The database schema is not automatically updated safely just because a Python model changed.

---

## 16. Why migrations are needed

Without migrations, teams may change database schemas manually or recreate tables. This creates problems:

- changes are difficult to review;
- environments become inconsistent;
- production changes are hard to reproduce;
- rollback is unclear;
- deployment order becomes risky.

Migrations provide:

- version history;
- repeatability;
- reviewable schema changes;
- consistent development, test, staging, and production environments;
- a record of how the schema evolved.

Migration files should be committed to version control.

---

## 17. Model change versus migration

Suppose a developer adds this field to the Python model:

~~~python
category: str
~~~

This changes the application's expectation, but it does not automatically add a category column to an existing production table.

A safe workflow is:

1. Change the model.
2. Generate or write a migration.
3. Review the migration SQL.
4. Test it against a realistic database.
5. Apply it in the correct deployment process.
6. Deploy application code that uses the new schema.

In production, schema changes and application changes may need to be deployed in a backward-compatible order.

---

## 18. Expand-and-contract migrations

For risky changes, use an expand-and-contract approach.

### Expand

Add the new schema without immediately removing the old schema.

Example:

- add a new nullable column;
- deploy code that can read both old and new fields;
- backfill existing records;
- begin writing the new field.

### Contract

After all application instances use the new schema:

- stop writing the old field;
- verify old data is no longer needed;
- remove the old column in a later migration.

This approach is useful because multiple application instances may run different code versions during a rolling deployment.

---

## 19. Migration risks

A migration can affect production availability.

Risks include:

- table locks;
- long-running rewrites;
- blocking reads or writes;
- adding a non-null column without a safe default;
- large backfills in one transaction;
- dropping data too early;
- incompatible application and schema versions;
- migrations running concurrently.

A technical lead should ask:

- How long will this migration run?
- Will it lock a large table?
- Is it backward compatible?
- Can it be rolled back or repaired?
- How will progress be monitored?
- What happens during partial deployment?
- Is the migration safe to run more than once?

---

## 20. Common mistakes

- Assuming an ORM eliminates the need to understand SQL.
- Treating an ORM session as the same thing as a database connection.
- Calling commit without understanding the transaction boundary.
- Forgetting rollback after an exception.
- Holding an ORM session or connection while calling an external service.
- Triggering N+1 queries through lazy relationship loading.
- Returning entire related objects when only a few fields are needed.
- Changing a model without creating a migration.
- Editing production tables manually without a migration record.
- Running a large backfill inside one long transaction.
- Removing old columns before all application versions stop using them.
- Trusting automatically generated migrations without reviewing them.

## Mental model

~~~text
ORM model       → application representation
ORM session     → unit of work and object tracking
Repository      → persistence boundary
Generated SQL   → database operation
Migration       → versioned schema change
Database        → durable state and constraint authority
~~~
